## 1. Environment decision: CAGE Challenge 4 (CC4)

Why: CC4 is the CAGE benchmark designed for multi-agent RL. It has **5 Blue agents** (one per security zone, one covering three zones), a PettingZoo-style parallel API, green (user) agents, a Red agent (`FiniteStateRedAgent`), mission phases, randomized topology per episode, and restricted **8-bit messages** between some agents. CAGE 2 has a single Blue agent, so it cannot honestly support "multi-agent".

Repo: https://github.com/cage-challenge/cage-challenge-4 (install instructions in its README / docs, Python 3.10+ recommended).

Useful things already in the repo (read these before writing code):
- `CybORG/Evaluation/training_example/TrainingSB3.py`: PettingZoo shim + `MaskablePPO` (sb3-contrib).
- `CybORG/Evaluation/training_example/TrainingRay.py`: RLlib multi-agent example (DQN; switchable to PPO).
- `CybORG/Evaluation/evaluation.py`: official evaluation (100 episodes of 500 steps vs `FiniteStateRedAgent`).
- `CybORG/Agents/Wrappers/`: `BlueFlatWrapper`, `BlueFixedActionWrapper`, `EnterpriseMAE`, `BlueEnterpriseWrapper`.
- The training examples use 100-step episodes for speed. The official evaluation uses 500.

**Gate (decide at the end of Phase 1):** if CC4 cannot be installed and run a random-agent episode within 2 days, fall back to CAGE 2 (Phase 1B below) and say so in the report. Do not fall back to a fake environment.

**Phase 1B fallback (CAGE 2 only):** real CybORG CAGE 2 with the existing `run_baselines.py`, a stronger rule-based agent, and single-agent PPO (Stable-Baselines3). MARL then becomes a clearly-labelled limitation or future work.

## 4. Phases

### Phase 1: Environment running (Days 1-2)
Tasks:
1. Create a Python 3.10+ venv. On Windows, use WSL2 for anything involving Ray (RLlib support on native Windows is limited). Colab or Kaggle is the fallback for training.
2. Clone cage-challenge-4, install per its README, run its tests or the example submission.
3. Write `envs/cc4_env.py`: builds `EnterpriseScenarioGenerator(blue_agent_class=SleepAgent, green_agent_class=EnterpriseGreenAgent, red_agent_class=FiniteStateRedAgent, steps=N)`, wraps it as in the training examples.
4. Write a script that runs 5 episodes with a Sleep Blue team and prints, per step: red activity, blue actions, reward.

Acceptance: 5 random-team episodes complete; printed rewards are penalties (non-positive; check the Table 4 penalties in the CC4 README); different seeds give different topologies.

### Phase 2: Baselines (Days 2-3)
1. `agents/baselines.py`: Sleep, Random (respecting action masks), and a stronger rule-based team (e.g. when an alert or a compromised host appears in its zone, Analyse then Remove, then Restore if needed).
2. `experiments/run_baselines.py`: 100 episodes per baseline (use 100 steps for dev, 500 for the final table), 3 seeds. Writes `results/tables/baselines.csv`.

Acceptance: Sleep is clearly worse than the rule-based team; numbers are reproducible with the same seed.

### Phase 3: Independent PPO (Days 3-6)
1. Adapt `TrainingSB3.py` (MaskablePPO with a PettingZoo shim, parameter sharing across agents) or `TrainingRay.py` (PPO, one policy per agent).
2. `experiments/train.py --algo ippo`: logs mean team return per N episodes to `results/training/ippo_seed{N}.csv`; saves checkpoints.
3. Train 3 seeds. Start with 100-step episodes for speed.

Acceptance: learning curve trends upward; trained policy beats Sleep and Random on held-out seeds.

### Phase 4: MAPPO (Days 6-9)
1. Implement a centralized critic over the joint observation (pad observation sizes; `pad_spaces=True` exists in `BlueEnterpriseWrapper`, verify in source), with decentralized actors. Reuse the existing `agents/mappo.py` logic but adapt dimensions and add action masking.
2. Use PettingZoo parallel API; handle variable action sizes per agent by masking.
3. Train 3 seeds, same budget as IPPO (same number of environment steps).

Acceptance: both algorithms evaluated on the same seeds; mean ± std table; honest write-up even if MAPPO does not beat IPPO (the AAAI CC4 paper discusses how hard this benchmark is, so a modest result is acceptable if explained).

### Phase 5: LLM orchestrator (Days 9-12)
Design (keep the LLM out of the training loop):
1. `llm/summarize.py` converts the current alerts and observations into a short text summary (counts per zone, recent alerts, current mission phase).
2. Mode A, **advisory**: every K steps (e.g. 25) the LLM receives the summary and returns validated JSON (zone priorities, flagged conflicts) plus a short incident report. This produces reports and per-zone priorities and does not change actions. Evaluate report quality and latency/cost.
3. Mode B, **intervening** (the experiment that can show a real effect): the LLM's zone priorities are used at the moment of a limited decision, e.g. choosing which zone's costly action (Restore, firewall close) is allowed when several agents propose one in the same window, versus a fixed-priority rule. Compare return with and without it. No reward bonus of any kind.
4. Call budget: free-tier limits apply. Call only every K steps or on alert bursts. Cache by prompt hash. Use ~10 episodes for the LLM variants, not 100.
5. Without a key or on API failure: the run must be labelled `source: fallback` or fail loudly; never mix fallback outputs into LLM results.

Acceptance: logs contain real latency and token counts; a table compares RL-only vs RL + LLM-advisory vs RL + LLM-intervening on identical seeds.

### Phase 6: Dashboard (Days 12-14)
Streamlit app that only reads `results/`:
1. **Live Episode**: select agent, red strategy, seed; step slider and play button; zone/subnet graph colored by host state; per-step event log; reward curve. A badge shows the data source (`CC4 real rollout`).
2. **Compare**: two agent teams replayed side by side on the same seed.
3. **Training**: learning curves, mean ± std over seeds, IPPO vs MAPPO.
4. **LLM Orchestrator**: input summary, JSON output, incident report, latency, cost, `source` badge.
5. **Architecture**: diagram, Dec-POMDP framing, algorithm notes.
Pre-generate replays offline; the demo only plays them back. Record a backup screen capture.

### Phase 7: Report and viva prep (last 3 days)
- Update the existing report with CC4, results tables, limitations, and the honest note about what the LLM does and does not improve.
- Prepare 8-10 minute demo flow: problem, architecture, baselines, Compare-tab demo, training results, LLM layer, limitations.

## 7. Likely viva questions (prepare honest answers)

- Why CC4 and not CAGE 2? (Multi-agent by design; 5 Blue agents.)
- Why is the LLM not inside the RL loop? (Latency, cost, non-determinism, reproducibility.)
- What does the LLM actually change? (Show Mode A and Mode B results, including if the effect is small.)
- What is CTDE and why use it? (Centralized critic helps credit assignment; actors only use local observations at execution.)
- How do you know the results are not luck? (Seeds, std, same budget.)
- What are the limitations? (Compute budget, shorter training, free-tier LLM limits, simulator only.)
